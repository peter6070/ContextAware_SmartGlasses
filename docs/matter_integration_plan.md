# 노트북 직접 Matter 제어 계획

## 목표와 현재 상태

기존 미니어처 장치에 헤이홈 스마트 플러그 Air를 추가합니다. Home Assistant, 헤이홈 앱, 스마트폰 앱 또는 별도의 스마트홈 허브를 사용하지 않고, Windows 노트북에서 실행하는 이 프로젝트가 기기 등록과 제어를 담당합니다. 플러그를 선택하는 입력은 기존과 같이 ArUco 마커와 손 제스처를 사용합니다.

2026-11-17 기준: 플러그 Air를 보유하고 공장 초기화 상태라는 점은 사용자 제공 정보입니다. 제조사는 [플러그 Air의 Matter 연동](https://hej.life/article/%EC%83%81%ED%92%88-qa/6/108344/)을 안내합니다. **실제 보유 제품의 세부 모델, Matter 전송 방식, Windows 노트북의 BLE 동작 및 직접 등록 성공 여부는 미검증**입니다. 로컬 Matter 컨트롤러와 등록·제스처 분기 시제품 및 마커 4를 작성했습니다. 실기기 등록·제어, LCD 표시 및 네트워크 이동은 아직 검증되지 않았습니다.

## 필수 조건: 장소가 바뀌어도 사용할 수 있는 네트워크

가정뿐 아니라 학술제와 공공시설에서도 동작할 수 있어야 합니다. 특정 SSID, IPv4 대역이나 고정 IP에 의존하지 않고 카메라와 플러그를 다시 찾아 연결하며, 네트워크 변경 후 등록된 플러그의 연결 복구를 시험합니다. 단, 외부 네트워크의 차단 정책을 프로그램만으로 해제할 수는 없으므로 **모든 공공 Wi-Fi에서의 무조건적인 동작은 보장하지 않습니다**. 현장 네트워크가 필요한 통신을 차단할 때도 시연할 수 있는 대체 네트워크를 준비하는 것이 완료 조건입니다.

1. 현장 Wi-Fi에서 플러그·노트북·카메라가 연결될 수 있는 인증 방식과 대역을 확인합니다. 장치 간 직접 통신, IPv6, mDNS/DNS-SD 및 필요한 멀티캐스트가 동작하는지 시험합니다. 같은 Wi-Fi 이름으로 연결되더라도 클라이언트 격리 또는 방화벽 때문에 실패할 수 있습니다. 카메라 스트림과 Matter 제어를 각각 진단합니다.
2. 공공망이 차단하면 노트북의 모바일 핫스팟을 **후보**로 시험합니다. 노트북과 카메라·플러그 사이의 통신, 특히 Matter가 요구하는 IPv6와 탐색이 실제 Windows·무선 어댑터 조합에서 작동할 때에만 채택합니다. 핫스팟이 충분한 IPv6/멀티캐스트 연결을 제공한다고 가정하지 않습니다.
3. 핫스팟도 실패하면 호환되는 휴대용 공유기 등 직접 관리 가능한 로컬 Wi-Fi를 **대안으로 검토**합니다. 이는 Matter 스마트홈 허브나 스마트폰 앱과는 다른 네트워크 장비이지만, 추가 장비를 사용하므로 실제 채택 전에 사용자 선택이 필요합니다. 해당 환경도 실장치로 검증합니다. Wi-Fi 방식 플러그를 전제로 하며 제품의 실제 전송 방식은 미확인입니다.
4. 최초 등록과 네트워크 변경 시 Wi-Fi 자격 증명 제공, 기존 Fabric 유지 및 기기 재등록 필요 여부를 실제 플러그에서 확인합니다. 인터넷이 없는 상태에서의 등록과 등록 후 제어는 별개의 시험 항목입니다.

`127.0.0.1` 등 `127.0.0.0/8`은 기기 자신의 루프백 주소이므로 노트북 내부의 어댑터 통신에는 쓸 수 있지만 다른 카메라나 플러그의 주소로 쓸 수 없습니다. `192.168.x.x`, `10.x.x.x`, `172.16~31.x.x` 등 주소 형식 자체로 장소나 연결 가능 여부를 판단하지 않습니다. Matter 연결은 IPv6 지원과 탐색 경로도 중요합니다. [IETF 루프백 주소 설명](https://datatracker.ietf.org/doc/html/rfc5735), [Matter 사양의 IPv6 및 DNS-SD](https://csa-iot.org/wp-content/uploads/2023/10/Matter-1.2-Core-Specification.pdf).

## 제안 구성

```text
ESP32-S3-CAM ── Wi-Fi 영상 ──> 노트북의 Python 인식 프로그램
                                  │
                                  ├─ 마커·제스처 → 기존 장치 → USB → Arduino → LED/서보/팬
                                  │                                      └→ I2C LCD
                                  └─ 마커·제스처 → 로컬 Matter 어댑터 → 플러그 Air
                                                        │
                                           초기 등록: 노트북 BLE + 설정 코드
                                           등록 후: 해당 기기의 Matter IP 네트워크
```

- 노트북이 Matter 컨트롤러를 실행합니다. 스마트홈 서비스나 모바일 앱을 거치지 않습니다. Matter SDK와 그 실행 환경은 이 프로젝트의 로컬 소프트웨어 의존성입니다.
- 우선 후보는 Node.js 기반 [matter.js](https://github.com/matter-js/matter.js)와 [BLE 패키지](https://github.com/matter-js/matter.js/tree/main/packages/nodejs-ble)를 이용하는 로컬 어댑터입니다. Python이 로컬 자식 프로세스에 구조화된 요청을 보내고, 어댑터가 등록·장치 검색·상태 읽기·명령을 처리하는 방식을 제안합니다. 별도 서버 제품이나 Home Assistant 없이 같은 노트북에서만 실행합니다. SDK의 Windows BLE 호환성과 대상 플러그에서의 성공은 실증 전까지 보장하지 않습니다.
- [matter.js의 컨트롤러 예제](https://github.com/matter-js/matter.js/tree/main/examples/controller)는 설정 코드와 BLE를 이용한 등록 및 Wi-Fi 정보 전달을 설명합니다. 실제 구현 시 지원하는 버전과 Windows BLE 드라이버 요구사항을 고정·검증합니다. 예제의 동작이 곧 해당 플러그에서의 성공을 의미하지는 않습니다.
- 플러그가 Matter over Wi-Fi라면 노트북과 플러그가 IP 통신이 가능한 Wi-Fi 네트워크에 연결되어야 합니다. 기존 공유기를 사용할 수 있으며, 카메라 영상과 Matter가 통신할 수 있는 동일한 로컬 네트워크 구성을 우선 검토합니다. 인터넷 없는 운영 가능 여부와 최초 등록 중 외부 검증에 필요한 접속 여부는 실제 환경에서 별도로 시험합니다.
- 만약 제품이 Matter over Thread라면 호환되는 Thread 무선 장치 및 Border Router 구성이 필요합니다. 이를 노트북 단독으로 해결할 수 있다고 가정하지 않습니다. 플러그 Air의 실제 방식은 제품 표기나 제조사 자료로 확인합니다.

## 등록 및 제어 사용자 흐름

1. 노트북에서 프로젝트의 등록 명령을 실행하고, 플러그의 숫자 Matter 설정 코드 또는 QR 코드 내용을 **로컬에서 직접 입력**합니다. 최초 버전은 숫자 코드 입력을 우선하고 QR 카메라 스캔은 후속 기능으로 둡니다. 코드를 대화창이나 저장소에 공유하지 않습니다.
2. 기기를 페어링 모드로 두고, Wi-Fi형인 경우 노트북 BLE로 기기를 찾아 로컬 네트워크 정보를 전달하는 방식을 우선 시험합니다. 노트북에서 사용할 수 있는 BLE 어댑터와 권한, 대상 제품이 해당 방식을 지원하는지 확인합니다.
3. 등록 성공 시 컨트롤러의 Fabric 자격 증명과 장치 식별자를 노트북 로컬의 접근 제한된 저장소에 보관하고, 사용자가 알아볼 이름을 지정합니다. 비밀번호·설정 코드·개인 키를 콘솔 로그, 버전 관리 또는 명령행 인자에 노출하지 않습니다. 입력과 저장 방식은 OS 권한을 고려하여 구현 단계에서 검증합니다.
4. 등록 후 플러그의 실제 엔드포인트와 On/Off 기능을 조회하고, 사용자가 마커 ID를 장치에 연결합니다. 첫 플러그에는 ID 4를 **제안**합니다. 엔드포인트 번호를 임의로 고정하지 않습니다. 여러 기기와 마커는 설정 파일의 비밀이 아닌 식별자로 확장합니다.
5. ID 4가 안정적으로 선택되면 플러그를 대상으로 합니다. 주먹 → 손바닥은 켜기, 손바닥 → 주먹은 끄기입니다. 마커 검출만으로는 전원을 변경하지 않습니다.
6. 장치를 등록하지 않았거나 응답이 없으면 실패를 표시합니다. ON/OFF 명령에 대한 응답과 별도로 가능한 경우 기기 상태를 읽거나 구독하여 확인하며, 연결 실패·상태 미확인을 성공으로 표시하지 않습니다. 중복 입력에는 토글 대신 명시적인 On 또는 Off 명령을 사용합니다.

## 기존 코드와 LCD 연동 설계

- 현재 `software/config.py`는 마커 1~3만 알고 `command_router.py`는 Arduino 명령만 생성합니다. 설정에 기기 유형과 마커 ID를 추가하고, 공통 명령을 `arduino` 또는 `matter` 백엔드로 분기합니다. 기존 설정과 마커 1~3의 동작은 유지합니다.
- 현재 Arduino는 `SELECT,LIGHT/CURTAIN/FAN/NONE`만 허용합니다. 따라서 `PLUG`를 그대로 전송하면 거부됩니다. 구현 시 플러그 선택 전환에서 먼저 기존 Arduino 선택을 `SELECT,NONE`으로 해제하고, Matter 장치용 별도 LCD 표시 프로토콜을 추가합니다. LCD 표시 요청은 Arduino 액추에이터 선택 또는 구동을 유발해서는 안 됩니다.
- LCD에 표시할 때 플러그 이름과 **확인된 기기 상태**를 표시하고, 조회 전·실패·오프라인은 `--` 또는 별도 오류로 표시합니다. 기존 Arduino 장치의 `CMD:ON/OFF`는 명령 이력으로 유지해 의미를 구분합니다. LCD가 없거나 Arduino가 연결되지 않아도 Matter 제어가 가능한 구조를 목표로 합니다.
- Matter 연결, 등록 및 제어는 영상 루프를 장시간 막지 않도록 별도 작업으로 처리합니다. 선택이 바뀐 뒤 뒤늦게 도착한 응답은 현재 선택의 상태로 잘못 표시하지 않습니다. 요청마다 식별자·타임아웃을 두고 재시도 여부와 중복 처리를 명시합니다.
- 컨트롤러의 저장 데이터가 사라지거나 다른 노트북으로 옮겨지면 재등록이 필요할 수 있습니다. 초기화·등록 해제는 사용자가 명시적으로 실행하는 별도 동작으로 설계합니다.

## 구현 순서 및 검증 기준

1. **환경 실증:** 노트북의 Windows 버전·BLE, Wi-Fi/IPv6/mDNS, 제품 모델 및 네트워크 방식을 확인합니다. matter.js의 Windows 환경을 격리된 개발 환경에서 준비하고 BLE 발견 여부를 확인합니다. 통신 방식이 Thread이거나 노트북 BLE가 작동하지 않으면 기기 등록 완료를 가정하지 않고 필요한 장비·환경을 명시합니다.
2. **단독 등록 및 제어:** 로컬 컨트롤러로 초기화 상태의 플러그를 등록하고 엔드포인트를 조회한 뒤 명시적 On/Off와 실제 출력 및 상태 읽기를 확인합니다. 노트북 프로그램을 재시작해도 재등록 없이 연결되는지 시험합니다. 성공 전에는 Matter 통합을 완료로 표시하지 않습니다.
3. **프로젝트 통합:** 마커 4 선택, 제스처 전환, 백엔드 분기를 구현합니다. 미등록·미선택·연결 실패 시에는 플러그가 작동하지 않는지, 기존 Arduino 장치가 선택·구동되지 않는지 검증합니다.
4. **LCD와 오류 처리:** 플러그 선택 및 실제 조회 상태·오류를 표시하고, LCD 미연결에서도 플러그 제어가 가능한지 확인합니다. 장치 연결 끊김, 재연결, 시리얼 응답 지연, 잘못된 설정 코드 및 중복 명령을 시험합니다.
5. **시연 검증:** 가정용 네트워크와 실제 학술제 공공망에서 마커→선택→제스처→플러그 실제 ON/OFF, 선택 변경, 네트워크 단절, 재시작 후 복구 및 기존 장치 회귀 시험을 기록합니다. 공공망이 차단될 때는 검증된 대체 네트워크에서 동일한 종단 시험을 완료합니다. 영상·Matter 네트워크의 실제 지연과 안정성을 측정합니다. 현장 테스트 전에는 이 필수 조건을 완료로 표시하지 않습니다.

실제 플러그 시험은 제품 정격에 맞는 부하로 진행하며, 네트워크나 노트북 장애 시 전원 상태가 어떻게 되는지 제품 특성을 확인합니다.
